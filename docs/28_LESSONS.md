## 1. 아키텍처: 처음부터 데이터 지향으로 할까 (장르별 판단)
Roblox 기본은 "Part = 게임 객체"(엔진 물리 + 자동 복제). 객체 수가 많아지면 서버 물리·위치 복제가 병목이 되고, 나중에 데이터 지향으로 바꾸면 거의 모든 시스템을 다시 짜야 한다 (docs/27).

### 1.0 규칙: 기획 단계에서 부하를 예상하고, 그 숫자로 ECS·데이터 지향 여부를 정한다
프로젝트 시작(GDD·기술 설계) 때 아래 계산을 문서에 남기고 결정한다. "나중에 렉 나면 바꾸자"는 이번처럼 5단계 전환 비용이 든다.

1. **최악 장면을 정한다**: 최대 인원(서버 크기) × 후반 플레이어 한 명이 동시에 가진 움직이는 객체 수, 초당 생성·삭제 수.
2. **서버 물리 예상** ≈ 최대 인원 × 플레이어당 움직이는 Part 수 × **0.045ms**
   (이 프로젝트 실측: 고정 안 된 Part 56개 + 초당 생성 14·삭제 23인 트레이 하나 = 2.55ms. 생성·삭제가 적으면 더 낮다. 다른 PC·장르면 프로토타입에서 다시 잰다.)
3. **판정** (서버 프레임 예산 16.7ms 기준):

| 예상 서버 물리 (최악 장면) | 결정 |
|---|---|
| 5ms 이상 | **처음부터 데이터 지향**: ECS 저장소 + 자체 간이 물리 + buffer 복제 + 클라 로컬 렌더 (docs/27 구조) |
| 2~5ms | Part로 시작하되 **객체 접근을 한 모듈 API로**, 백엔드 교체 자리와 측정용 디버그 명령을 처음부터 (전환이 1주 → 며칠) |
| 2ms 미만 | 기본 Part 방식 |

4. 같이 볼 것: 플레이어당 서버 전송 kbps(움직이는 객체 위치는 데이터 지향이어도 보내야 한다 — 이번엔 두 방식 모두 ~45kbps), 클라 초당 인스턴스 생성 수(풀로 해결).
5. 첫 플레이 가능 빌드에서 디버그 명령으로 최악 장면을 재현해 실측하고, 예상과 2배 넘게 다르면 결정을 다시 본다.

아래 질문은 숫자를 내기 어려운 초기 판단용이다.

| 질문 | 예 → 처음부터 데이터 지향 | 아니오 → 기본 Part 방식 |
|---|---|---|
| 같은 종류 움직이는 객체가 플레이어당 수십 개 넘게, 서버 전체 수백 개 넘게 생기나? | 머지·타이쿤 큐브, 탄막, 군중, 농장 작물 | 캐릭터 몇, 소품 몇 |
| 객체가 초당 여러 개 생기고 사라지나? | 드로퍼·스포너 경제 | 레벨에 고정 배치 |
| 객체끼리의 물리가 "결과"만 중요한가? (쌓임·합치기 판정) | 간이 물리/격자로 충분 | 래그돌·차량·실제 물리가 재미의 핵심 |
| 플레이어 캐릭터와 부딪혀야 하나? | 아니면 쉬움 (서버 판정 + 클라 연출) | 그렇다면 클라 소유 물리 + 검증이 필요해 비용 큼 |

- 데이터 지향 = 서버는 상태(id·등급·위치)만, 간이 물리는 직접(공간 해시 + 위치 기반 동역학), 복제는 buffer 스냅샷(움직이는 것만), 클라이언트가 로컬 Part로 보간 렌더링.
- 처음부터 하면 비용 작다: 저장소(ECS 열) + 코덱 + 뷰 3개 모듈을 먼저 두고 게임 시스템은 id로만 다룬다.
- 그래도 시작은 Part로 프로토타입해도 된다. 단, **객체 접근을 처음부터 한 모듈 API로 모아 둘 것** (`cube.part`를 여기저기서 만지면 전환 비용이 폭증, docs/27 단계 1).
- 간이 물리는 회전이 없으면 막히는 경우가 반드시 생긴다(사이에 낀 큐브에 막힌 짝, 외줄 탑). "몇 번 시도해도 안 되면 결과로 처리"하는 안전장치를 처음부터 둔다 — 물리는 연출, 결과는 데이터 (docs/27 단계 5).
- 전환은 플래그로: 같은 장면을 두 방식으로 재서 표로 비교하고, 끄면 바로 예전 동작 (docs/27).
- 측정 기준: 마이크로프로파일러 서버 물리 ms, 서버 전송 kbps, 클라이언트 초당 인스턴스 생성 수 (docs/06 "고등급 렉" 표).

## 2. 성능
- 렉 원인은 객체 크기가 아니라 **초당 생성·삭제 수**. 효과음·연출 파트는 풀로 재사용 (docs/06).
- 움직이는 객체 복제는 데드 레코닝: 서버·클라가 같은 예측식(공용 순수 모듈)을 쓰고 예측이 틀어질 때만 보정을 보낸다 (스냅샷 −42%, docs/27 최적화).
- 클라 로컬 파트도 풀로: 부모를 떼어 두었다가 다시 넣는다. 다른 모듈이 남긴 화면 상태(흐림·꺼짐 표시)는 넣을 때 되돌린다.
- 연출은 초당 예산을 두고 넘으면 가볍게 (합치기 연출 초당 8개).
- 꾸밈(Decal·SurfaceGui·빛)은 서버가 만들지 말고 속성만 복제, 클라이언트가 붙인다 (client/CubeLook).
- 먼 플롯은 LOD로 꾸밈 끄기, 남의 연출은 거리·빈도 제한.
- Highlight는 31개 제한 → 많이 쓰면 SelectionBox. Glass 재질 뒤 투명 물체는 안 그려진다.

## 3. 경제·진행 설계
- 경제 공식은 순수 모듈 + 오프라인 시뮬레이터(tools/pacing_sim.py)로 먼저 맞추고 게임에 넣는다 (docs/13).
- 리버스 조건은 "돈"만이 아니라 "목표 등급 달성"을 같이 (돈만이면 컨텐츠를 보기 전에 넘어감, docs/13 §9.9).
- 확률 상품은 Robux로 사지 않게 (유료 랜덤 금지), 확률은 UI에 그대로 표시.

## 4. Roblox 플랫폼
- 서버 크기는 플롯 수와 맞춘다 (50 vs 8 플롯 → 9번째 사람 튕김, docs/26).
- 추천 신호: 들어오는 비율(썸네일) → 첫 1~3분 이탈 → 재방문일 → 플레이 시간(하루 60분 상한) → 함께 논 날 (docs/26).
- 성숙도 설문·장르·썸네일 여러 장은 공개 전에 끝낸다.
- TikTok 홍보: 웹 Studio 예약 + 10MB로 재압축한 파일은 조회수 0이었고, 원본을 API 수신함(video.upload) → 앱에서 게시하면 정상 노출 (marketing/shorts_schedule.md). 미심사 앱은 Direct Post 불가라 게시 탭은 사람이 한다.
- Open Cloud 키 권한은 처음에 필요한 범위를 정해 둔다 (`universe.place:write`가 없어 서버 크기 변경 403).

## 5. 작업 방식 (에이전트·도구)
- Studio MCP: 편집 모드 코드 동기화는 HTTP 로컬 서버 + GetAsync로 Source 설정. 클릭은 instance_path로.
- 디버그 명령(StudioDebug)을 처음부터: 재화·상태 주입, 후반 재현(리버스·드로퍼 설정), 저장/복원.
- 모든 변경은 check.ps1(luau-lsp·selene·stylua·Lune 테스트·rojo build) 통과 후 커밋.
- 큰 전환은 단계로 나누고 단계마다 게임이 계속 돌아가게(플래그로 새 경로 전환), 난이도에 따라 모델을 나눠 맡긴다 (docs/27 §2).

## 6. 여러 게임 운영
- 공개 기준은 Merge Cube Factory 수준의 기능 묶음 (사용자 결정, docs/30 §1.1). 문서·도구·공용 코드로 그 수준까지의 기간을 줄이고, 공개 후 14일 측정 → 집중·보관 (docs/30).
- 공용으로 옮기는 건 두 번째로 쓰일 때. 집중 게임은 동시에 1~2개 (docs/30 §1·§3).

## 7. 번역
- 숫자·이름이 들어가는 화면 글자는 처음부터 키 + 매개변수(`Loc.set`, shared/Strings)로. 고정 문장은 자동 캡처에 맡긴다. 나중에 바꾸면 100곳 넘게 고친다 (docs/31 §2).
- 서버는 글자 대신 `{key, args}` 표를 보낸다. FormatByKey에 숫자를 그대로 넘기면 "3.00"이 되므로 글자로 바꿔 넘긴다.
- 숫자뿐인 라벨·플레이어 이름은 `AutoLocalize = false` (캡처 할당량 낭비·이름 수집 방지).
