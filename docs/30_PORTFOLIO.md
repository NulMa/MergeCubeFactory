# 30. 여러 게임 포트폴리오 운영 — 많이 내고, 유입이 생기는 게임에 집중

> 사용자 (2026-10-25): "앞으로 이런 게임을 nn개 만들어서, 그 중에 유입이 생기는 게임을 중점으로 개발할지도 몰라. 그에 대한 기획이나 대처, 노하우 등도 잘 정리해두길바래".
> 이 문서 = 전략·관문·재사용·대처. 개별 교훈은 `docs/28_LESSONS.md`, 추천 신호는 `docs/02`·`docs/26`, 지표는 `docs/09`.
> 수치 중 "가정"이라고 쓴 것은 실측이 없는 출발값이다. 게임 3~5개 실측이 쌓이면 이 문서의 관문 수치를 그 분포로 바꾼다.

## 0. 왜 포트폴리오인가 / 첫 게임에서 배운 것
- Roblox 추천은 **이미 잘 되는 게임에 노출을 더 준다** (플레이 전환율·첫 플레이 이탈·재방문·플레이 시간, docs/02 §1). 어떤 컨셉이 그 고리에 올라탈지는 내보내 보기 전엔 모른다. 그래서 작게 여러 개를 내고, 신호가 오는 것에 시간을 몰아준다.
- Merge Cube Factory(첫 게임) 타임라인: 10/17 시작 → 9일, 커밋 122개, 시스템 20개 이상(머지·변이·도감·펫·레이드·훔치기·배트·봇·출석·이벤트…).
  - **유입 시도 기준 = 지금 수준의 기능** (사용자 2026-10-25 "유입 시도는 지금 정도의 기능 구현을 했을 때를 기준으로 할거야"). 최소 기능으로 먼저 내지 않는다. 대신 이번에 쌓은 문서·도구·공용 코드로 **같은 수준에 도달하는 기간을 줄인다** (목표: 9일 → 4~5일, §1).
  - 9일 중 시간이 많이 든 것 (다음엔 처음부터 피함): 데이터 지향 전환(docs/27, 부하 예상으로 처음부터 결정), 큐브 크기·트레이 넘침 재조정(크기 공식을 등급 띠로 처음부터), 흔들림·연출 과다(연출 예산을 처음부터), 사용자 피드백 반복으로 고친 UX(버튼 배치·확인 탭·일괄 강화 — docs/05 패턴을 체크리스트로).
  - 잘한 것: 공용 코어(`src/core`)·검사(check.ps1)·디버그 명령·게시 스크립트·숏폼 빌더를 처음부터 둬서 다음 게임에 그대로 쓸 수 있다.

## 1. 한 게임의 생애: 관문 (Stage gate)
| 단계 | 목표 기간 | 할 일 | 다음으로 가는 조건 | 못 넘으면 |
|---|---|---|---|---|
| G0 컨셉 | 반나절 | 후보 3~5개를 `tools/concept_score.py`로 점수화 (수요·추천 적합·수익·독창성·자동화 가능성, docs/12). 핵심 재미를 **한 문장 + 5초 영상 장면**으로 쓴다 | 한 문장이 숏폼 첫 1초 훅이 되나 | 다음 후보 |
| G1 프로토 | 1~2일 | 핵심 루프만 (머지면 드롭→합치기→돈). 부하 예상 계산으로 데이터 지향 여부 결정 (docs/28 §1.0) | 사내 플레이 10분이 지루하지 않다, 첫 보상 ≤10초 | 버리거나 컨셉 수정 1회 |
| G2 공개 버전 | 3~4일 | **Merge Cube Factory 수준의 기능 묶음**(§1.1)을 게임에 맞게. 출시 체크리스트(docs/10), 썸네일 3장, 숏폼 3편, 자동 번역 켜기(docs/31) | 공개 | — |
| G3 측정 | 공개 후 7~14일 | 숏폼 하루 1편(그 게임 영상), 기능 추가 금지, 버그·첫 5분만 고침. 아래 §2 표를 매일 채움 | §2 "계속" 조건 | **보관**(§5) |
| G4 집중 | 지속 | §4 플레이북 | 2주마다 §2 다시 판정 | 단계를 G3 수준 유지로 낮춤 |

### 1.1 공개 기준 기능 묶음 (Merge Cube Factory v60 기준)
| 묶음 | 내용 | 가져올 곳 |
|---|---|---|
| 핵심 루프 | 장르 핵심(머지면 드롭→합치기→돈) + 업그레이드(일괄 강화 포함) + 리버스 | docs/13·14, `tools/pacing_sim.py`로 먼저 맞춤 |
| 첫 5분 | 손가락 안내, 첫 구매 ≤30초, 목표 막대 | client/Tutorial, docs/05 |
| 수집 | 변이·도감, 펫(확률 표시, 유료 랜덤 없음) | docs/16·24 |
| 사람 사이 | 훔치기·배트·보호(연속 털림 잠금)·도둑 잡기 연출, AI 플레이어로 빈 서버 채우기 | docs/22·29 |
| 재방문 | 출석 7일, 일일 퀘스트, 플레이 선물, 이벤트(황금 큐브·피버), 보스 레이드 | docs/17·23·25 |
| 수익화 | 게임패스·개발자 상품·특가 | docs/03, `tools/products.mjs`·`passes.mjs` (생성은 승인) |
| 꾸밈·연출 | 배트 스킨·오라·트레일, 연출 예산·흔들림 상한 | docs/20, client/Fx |
| 운영 | 저장·영수증 멱등·분석 이벤트·평가 부탁·친구 초대·서버 크기=플롯 수 | src/core, docs/21·26 |
| 번역·홍보 | 자동 번역, 숏폼, 커뮤니티 공지·알림 | docs/31 |

- **동시에 집중하는 게임은 1~2개**. 나머지는 G3 측정 중이거나 보관.
- 신작 제작(G1~G2)은 에이전트로 여러 개 병렬 진행해도 된다. "병렬 3개 이상이면 G2에서 멈춘다"는 근거 없는 문장이라 삭제(사용자 2026-10-27: 지금 상황과 무관). 집중 1~2개 규칙은 공개 뒤 운영(G4) 단계에만 적용.

## 2. "유입이 생긴다"의 판정
같은 기간·같은 홍보량으로 비교해야 공정하다: **공개 후 첫 14일, 숏폼 하루 1편, 광고비 0**.

| 지표 | 어디서 | 의미 | 계속 (가정) | 보관 (가정) |
|---|---|---|---|---|
| 노출 대비 플레이 전환율 | Creator Analytics > Acquisition | 썸네일·이름이 먹히나 | 포트폴리오 중앙값 이상 | 중앙값의 절반 미만 |
| 추천(Home) 유입 비중 | Acquisition 소스별 | 알고리즘이 밀어 주기 시작했나 — **가장 중요한 신호** | 증가 추세 | 0에 가까움 |
| 60초 안 이탈 | Engagement / 퍼널 | 첫 1분 | ≤ 40% | ≥ 60% |
| D1 재방문 | Retention | 다시 올 이유 | ≥ 15% | < 8% |
| 평균 플레이 시간 | Engagement | 붙잡는 힘 | ≥ 12분 | < 5분 |
| 숏폼 조회 → 방문 | 숏폼 조회수 vs 그날 방문 | 영상이 게임으로 이어지나 | 영상 다음 날 방문 증가 | 변화 없음 |
| 자연 유입 (홍보 없는 날 방문) | 일별 방문 | 스스로 사람이 오나 | 0이 아님, 증가 | 0 |

- 판정: "추천 유입이 생기고 + 첫 1분·D1 중 하나가 계속 조건" → **집중 후보**. 셋 다 보관 조건 → 보관.
- 첫 게임 하나만 있을 때는 중앙값이 없으니 가정값으로 보고, 3개째부터 표의 "중앙값"을 실제 분포로 바꾼다.
- 기록 위치: 각 게임 `docs/09_KPI_LIVEOPS.md` + 포트폴리오 한눈표(§7). 숏폼 성과는 `marketing/shorts_schedule.md` 성과 기록.
- 숫자는 Creator Analytics(웹)에만 있는 게 많다 → 사용자가 주 1회 화면 캡처를 주거나 로그인해 두면 에이전트가 표를 채운다. Open Cloud로 가져올 수 있는 것은 자동화한다 (docs/07 §1의 10단계).

## 3. 재사용: 두 번째 게임부터 빨라지는 부분
지금 저장소 구조(`game/src/core` 공용 + `game/src/<게임>` + `<게임>.project.json`)를 그대로 쓴다. 한 저장소 = 여러 게임.

| 이미 있음 (그대로) | 위치 | 비고 |
|---|---|---|
| 저장·영수증·재화 원장·네트워크 | `src/core` (Data·Receipts·Ledger·Net) | 게임 무관 |
| 검사·빌드·게시 | `game/scripts/check.ps1`, `tools/publish.mjs` | 유니버스·플레이스 ID만 바꿈 |
| Studio 동기화·디버그 명령 | 스크래치 `mkmanifest.py` 방식, `StudioDebug` | 다음 게임 첫날부터 |
| 상품·패스 생성 | `tools/products.mjs`, `tools/passes.mjs` | 생성은 사용자 승인 |
| 아이콘·썸네일·파티클 | `tools/make_*.py` | 색·글자만 바꿈 |
| 숏폼 | `marketing/make_gameplay_shorts.py` (자막·효과음 섞기), TikTok 수신함 업로드 `tools/tiktok.mjs` | 한 계정이 여러 게임을 홍보 |

| 게임 사이로 옮길 후보 (지금은 merge 안에 있음) | 옮길 때 |
|---|---|
| AI 플레이어(`server/Bots`) — 빈 서버 채우기 | 두 번째 게임이 멀티 상호작용이면 바로. 게임 고유 행동은 콜백으로 |
| 연출(`client/Fx`: 흔들림 예산·배너·팝업·섬광), UI 키트(`client/Ui`) | 두 번째 게임 시작 때 `core/client`로 |
| 출석·일일 퀘스트·평가 부탁·친구 초대 | 수치만 Config로 |
| 훔치기·배트 | 같은 장르(플롯 경쟁)일 때만 |

- 규칙: 공용으로 옮기는 건 **두 번째로 쓰일 때** (처음부터 일반화하지 않는다). 옮긴 뒤엔 두 게임 모두 check.ps1 통과.
- 컨셉 다양성: 같은 장르를 nn개 만들면 같은 알고리즘 칸에서 서로 경쟁한다. 장르는 섞되(머지/타이쿤/수집/파쿠르/협동), **재사용률이 높은 장르를 먼저** 고른다.

## 4. 집중(G4) 플레이북 — 신호가 온 게임
1. **신호의 원인부터 확인**: 어떤 숏폼·썸네일·기능 뒤에 올랐나 (게시일 표와 방문 그래프를 겹쳐 본다). 그 방향을 더 한다.
2. **첫 5분을 먼저**: 60초 이탈·첫 구매 퍼널을 매주 한 단계씩 고친다 (추천 1·2번 신호).
3. **주간 업데이트** (docs/09 §3): 매주 작은 콘텐츠 1개 + 버그 수정, 업데이트 이름을 게임 제목·설명에 (예: `[UPDATE]`). 격주 주말 이벤트(2배).
4. **서버·사람**: 서버 크기 = 플롯 수 (docs/26), 사람이 적으면 봇으로 채우되 `[BOT]` 표시는 유지(사람인 척 금지).
5. **수익화는 신호 뒤에**: 패스 가격·특가·구독은 동접이 생긴 뒤 A/B. 유료 랜덤 금지, 확률 표시 (docs/03).
6. **홍보 증폭**: 잘 된 숏폼 스타일로 하루 1~2편, Roblox 광고(스폰서)는 자연 유입이 생긴 뒤 소액 테스트 — 광고로 데려온 사람의 D1이 자연 유입과 비슷할 때만 늘린다.
7. **2주마다 재판정**: §2 표가 계속 조건에서 내려가면 업데이트 주기를 낮추고 다른 후보에 시간을 준다.

## 5. 보관(실패) 처리 — 버리지 말고 거둔다
- 게임은 **공개 상태로 둔다** (가끔 늦게 오르는 경우, 숏폼 하나가 뒤늦게 터지는 경우). 업데이트만 멈춘다.
- 보관 전 기록 (각 게임 `docs/28_LESSONS.md`에 3줄): 무엇을 기대했나 / 지표가 어땠나 / 다음 게임에 가져갈 것.
- 거둘 것: 공용으로 옮길 모듈, 잘 된 연출·UI, 숏폼 스타일, 썸네일 실험 결과.
- 서버 비용은 0이라 유지 비용은 "정책 변경 대응"뿐이다 → 분기마다 docs/02 금지 패턴 점검만.

## 6. 대처: 생길 수 있는 문제
| 상황 | 대처 |
|---|---|
| 한 게임이 갑자기 뜸 (동접 급증) | 서버 크기·플롯·DataStore 한도 확인, 신규 기능 동결하고 버그·렉만. `docs/06` 성능 표로 최악 장면 측정. 운영 게시 전 테스트 유니버스 확인 |
| 노출 제한·모더레이션 경고 | docs/02 §2·§4 점검표로 원인 찾고 고침, 같은 계정의 다른 게임에도 같은 패턴이 있나 일괄 점검 (계정 단위 위험) |
| 다른 사람이 베낌 | 업데이트 속도로 이긴다 (경쟁작 개선 속도 > 내 속도면 노출 감소, docs/09). 이름·썸네일 독자성 유지 |
| 우리 게임끼리 잠식 | 같은 장르 두 개가 같은 시기에 공개되지 않게 1~2주 간격 |
| 숏폼 조회수 0 | 웹 예약·재압축 금지, 원본을 수신함 → 앱 게시 (docs/28 §4). 첫 1초 훅·자막 점검 (marketing/ad_research.md) |
| 데이터 손실·영수증 오류 | core/Receipts 멱등, ProfileStore. 게임마다 같은 코어라 한 번 고치면 전부 |
| 키·계정 | 키는 `.secrets/`에만, 게임마다 최소 권한 키, Cubika 등 다른 유니버스는 건드리지 않음 |
| 작업량 폭발 (게임 수만큼 유지보수) | 집중 1~2개 규칙, 공용 코어로 수정 한 번에, 보관 게임은 업데이트 안 함 |

## 8. 다음 게임 시작 체크리스트 (첫날)
1. 컨셉 3~5개 점수화(`tools/concept_score.py`), 핵심 재미 한 문장 + 숏폼 첫 장면.
2. 부하 예상 계산 → 데이터 지향 여부 (docs/28 §1.0).
3. `game/<새게임>.project.json`, `src/<새게임>`, 테스트 유니버스·플레이스 ID, 최소 권한 키.
4. StudioDebug·check.ps1·publish를 첫 커밋에.
5. G2 범위를 표로 적고 그 밖의 기능은 WORKLIST "신호 뒤" 칸으로.
6. 공개 날 숏폼 3편 준비, 썸네일 3장, 서버 크기 = 플롯 수, 성숙도 설문.
